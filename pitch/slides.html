Problem & user

Fixing the books is scary when every click hits live data

Who

A beginner freelance bookkeeper or small-business owner in the US, 25–45, who keeps their own books in QuickBooks Online.

When

The monthly bank reconciliation turns up duplicates, wrong categories and a balance that doesn't match the statement.

The trap

Deleting the wrong row can make the balance match while the books are still wrong. A matching number feels like success, and that is exactly the mistake people need to practice catching.

How it works

Graded on the state of the books

1 · GivenA messy ledger and the bank statement (source of truth)
2 · YouDelete rows or change categories. Undo any time
3 · EngineRuns three independent checks on the result
4 · FeedbackPlain-language explanation of each broken rule

1 · Transactions

Every statement transaction is in the ledger exactly once: nothing real deleted, no duplicate left.

2 · Matches statement

Opening balance + ledger rows = statement closing balance, computed in integer cents.

3 · Categories

Every row fits its category rule. Independent of money: recategorizing never moves the balance.

Success only when all three pass. Any correct end state passes: either copy of a duplicate may be deleted; two real identical purchases are not a duplicate.

Engineering

The core loop is tested, not just shown

  • Pure TypeScript engine with no UI code; money as integer cents; immutable state; undo restores the exact previous state.
  • 18 unit tests (Vitest): correct, equivalent, deleting a needed row, compensating errors, wrong category at $0.00, identical purchases ≠ duplicate, exact undo.
  • Exhaustive test: all 16,384 keep/delete combinations of the 14 rows: exactly 2 pass (delete either duplicate copy).
  • 16-step end-to-end check in headless Chrome against the live URL, desktop and 375 px phone.
  • CI: every push runs tests and build before deploying to GitHub Pages.
  • Static site: no backend, no accounts, no data collected; an offline build is ready for the demo.
